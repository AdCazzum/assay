Discovery

How does an agent find one that offers the service it needs, without a hardcoded list?

Trust before payment

Is this stranger competent and honest? You have to decide before the money moves.

Micro-payments

Per-call, sub-second, cheap enough that a single API read is worth settling on chain.

Star ratings do not fix trust. A rating is an opinion, and you cannot slash an opinion. We wanted reputation that reflects whether a result actually held up.

the idea

Make every claim falsifiable, then put money behind it

1. A provider publishes

Capability, price, endpoint and its own track record as ENS text records, plus a bond posted on chain. One name, one lookup.

2. A requester reads, then decides

Resolves the name, reads the manifest and the reputation, and decides for itself whether the price is worth it. Nothing forces the decision either way.

3. It pays per call

Real HBAR on Hedera testnet. The transaction memo carries the request hash, so a payment is tied to the exact request it bought.

4. The result can be disproved

The answer carries factual block-stamped claims. Anyone can challenge one. A verifier re-derives it from The Graph at that same block. If the provider lied: bond slashed, ENS reputation written down.

the stack  ·  why each network, not which

Every network here is load-bearing

ENSSepolia · identity + reputation

Two text records under a subname: assay:manifest (capability, price, endpoint, bond, a verifierHash committing to the verifier's own source) and assay:rep (score, jobs, slashes, bond).

Why it is load-bearing: one human-readable name gets an agent the price and the track record in a single lookup, with no reputation service to trust. Subnames resolve through a wildcard resolver: one transaction to set up the parent, then zero transactions per provider onboarded.

Hederatestnet · pay, bond, slash

pay(amount, requestHash) writes the request hash into the transaction memo. The provider serves only after the mirror node confirms the transfer. postBond and slash move real HBAR on the same rail.

Why it is load-bearing: the bond is what gives reputation teeth. Without a real transfer to lose, a score is just a number nobody has to back.

The Graphmainnet · the source of truth

getTokenSignals(token, atBlock) runs block-pinned Uniswap v3 subgraph queries through the gateway: liquidity, age in blocks, transaction count, volume, top-pool concentration.

Why it is load-bearing: it is not just the provider's input, it is what the verifier queries independently at the same block. A block outside the indexed range fails loudly instead of quietly returning live data.

how it is built

TypeScript monorepo, ports and adapters

packages/
  core          the loop, the shared types, the ports. Knows nothing about rug-scores.
  registry      ENS adapter (ethers, Sepolia): manifest + reputation text records
  payments      Hedera adapter (@hashgraph/sdk): pay / bond / slash / mirror-node confirm
  graph         The Graph adapter: block-pinned subgraph queries through the gateway
  cap-rugscore  the one concrete capability: run() and, crucially, verify()
apps/
  mcp           the MCP server, nine tools. This is the product.
  provider      the provider service: returns 402 until a payment is confirmed
  watchdog      challenges a claim from the command line
  dashboard     renders the loop, and replays a captured run with no network at all

Capability = run() + verify()

A capability is only admissible on this rail if a third party can re-derive its claims. That constraint is the design.

Adapters behind ports

RegistryPort, PaymentsPort, GraphPort. Swapping ENS for another registry does not touch the loop.

MCP: the requester is a real agent

Nine tools, driven by a live Claude Code session. The buyer is not a script with a delay in it.

real vs staged  ·  stated up front

What is real, what is staged, what is missing

Real, never faked

Every Hedera value transfer (pay, bond, slash), signed and mirror-node confirmed. Every ENS read and write on Sepolia. Every Graph query, against live mainnet data. The verifier. The agent.

Value moves between two distinct accounts, which is what makes verifying an amount meaningful at all.

Staged, and disclosed on screen

The "lying provider" is createLyingRugScoreProvider, a declared test harness that runs the real capability and tampers with exactly one claim.

Everything downstream of it, the challenge, the verifier, the slash and the ENS write, is the same code a spontaneous challenge runs.

Honest gaps

A failed challenge should also cost the challenger a deposit; there is no escrow yet, so only the provider has skin in the game.

Settlement is not atomic across three networks, and the code does not pretend it is: status is recorded before the ENS write, so a failed write leaves a truthful status and a named error.

One provider, one capability, exercised end to end.

The lesson this build kept re-learning: unit tests pass on things the chain does not do. When the payment gate started checking the amount, the loop broke, because the mirror node reports a self-transfer as only the fee movement. Every test was green. Only the live run showed it. The fix was a second funded account, not a weaker check.

the part we could not have scripted

The agent genuinely decides

The demo prompt sets a goal and a budget. It never names the provider to distrust, the claim to check, or when to challenge. Same prompt, different providers, different outcomes it reached on its own: DECLINED against one carrying slashes, PAID against a clean one.

"the two providers' claims were four blocks apart, so a naive side-by-side comparison of their outputs would have been unsound reasoning even though it happened to point at the right answer. What actually convicted the second provider was re-deriving at its own stamped block."

Nobody told it that comparing two providers' outputs would be unsound, or that block-stamping is what makes a verdict safe. It worked that out, flagged it rather than burying it, and noted the unsound route would have reached the right answer anyway.

Transcripts are committed in apps/mcp/agent/transcripts/.

Assay

A reputation and payment rail for agent-to-agent services. ENS is the business card, Hedera is the cash register, and reputation is assayed against The Graph, not rated. Built at ETHGlobal Lisbon 2026.

The problem

Agents have started paying other agents, and three primitives are missing: discovery (who offers this service?), trust before payment (is this stranger honest?), and a cheap per-call rail. Star ratings do not solve trust, because a rating is an opinion and you cannot slash an opinion.

The idea

  • A provider publishes its capability (what it does, price, endpoint) and its track record as ENS text records, and posts a bond on chain.
  • A requester resolves the name, reads the manifest and the reputation, and decides for itself whether to pay. Nothing forces the decision either way.
  • It pays per call on Hedera, with the request hash written into the transaction memo.
  • The result carries factual, block-stamped claims. Anyone can challenge one; a verifier re-derives it from The Graph at that same block. If the provider lied, its bond is slashed and its ENS reputation is written down.
discover (ENS) -> read reputation (ENS) -> pay (Hedera) -> serve (The Graph)
   -> challenge -> verifier re-derives from The Graph -> slash (Hedera) + reputation write (ENS)

Why each network is load-bearing

ENS (Sepolia)

Identity and portable reputation in two text records, assay:manifest and assay:rep. One lookup gets an agent the price and the slash history. A wildcard resolver means one transaction for the parent name and zero per provider onboarded.

Hedera (testnet)

Pay, bond and slash as real signed transfers. The provider serves only after the mirror node confirms the payment. The bond is what gives reputation teeth: without a real transfer to lose, a score is a number nobody has to back.

The Graph (mainnet)

Block-pinned Uniswap v3 subgraph queries. Not only the provider's input: the verifier queries the same block independently. Out-of-range blocks fail loudly rather than returning live data, which would slash honest providers on data drift.

Architecture

packages/  core (loop, types, ports) · registry (ENS) · payments (Hedera) · graph · cap-rugscore
apps/      mcp (the MCP server, nine tools) · provider (402 gate) · watchdog · dashboard (offline replay)

TypeScript ESM monorepo, ports and adapters, no emit step. A capability is admissible on this rail only if it ships run() and verify(): claims a third party can re-derive. The requester side is a real Claude Code session driving the MCP server's nine tools (list_providers, discover, pay_and_call, verify_claim, challenge, rate, get_job, list_jobs, register_provider).
